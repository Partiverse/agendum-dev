# 03 · 数据模型与同步协议

> 承接报告 §5.2（数据概念模型）与 §6.3（本地优先与同步）。本文给出可直接建库的 DDL v1、同步协议 v1、冲突解决与 E2EE 设计。
> 设计原则：**本地权威**（客户端 SQLite 是唯一事实源，服务端只是加密的中继与序号分发者）、**字段级同步**（最小冲突面）、**可加密**（密文模式下服务端不可见负载）。

---

## 1. 实体关系概览

```text
Area 1─n Project 1─n Task (自嵌套 parent_id 子任务)
              │ n
TagGroup 1─n Tag ──n─m── Task
Task 1─n TimeBlock（时间块，关联日历事件）★扩展
Task 1─1 计时状态（estimate/actual 闭环）★扩展
Review（回顾报告快照）★扩展      AIMemory（AI 偏好记忆）★扩展
Perspective（保存的查询）        Oplog（同步变更日志）
```

与报告 §5.2 的差异说明：`estimate/actual` 落在 tasks 表（闭环数据就地可查）；`TimeBlock` 独立表因为一条任务可被多次排块；新增 `sync_state` 与 `oplog` 两张同步基建表。

### 2.1 公共同步列（所有实体表统一携带）

### 2.4 同步基建

```sql
CREATE TABLE oplog (                    -- 本地待推送/已推送日志
  local_seq INTEGER PRIMARY KEY AUTOINCREMENT,
  server_seq INTEGER,                   -- 服务端确认后回填
  device_id TEXT NOT NULL,
  lamport INTEGER NOT NULL,
  entity TEXT NOT NULL,                 -- task|project|tag|...
  entity_id TEXT NOT NULL,
  field TEXT NOT NULL,                  -- 字段名；'__row'=整行创建
  op TEXT NOT NULL,                     -- set|del
  value_blob BLOB,                      -- E2EE 模式：密文；开发模式：JSON
  value_meta TEXT,                      -- 明文元数据：类型/长度
  pushed_at INTEGER
);
CREATE INDEX idx_oplog_pending ON oplog(server_seq) WHERE server_seq IS NULL;

CREATE TABLE sync_state (
  device_id TEXT PRIMARY KEY,
  lamport INTEGER NOT NULL,             -- 本设备逻辑时钟
  last_pull_seq INTEGER NOT NULL,       -- 拉取游标
  last_push_at INTEGER
);
```

**收敛规则**：每个字段的最终值由服务端与客户端共同按 `(lamport, origin_device_id 字典序)` 裁决——lamport 大者胜，lamport 相同时按设备 ID 字典序稳定破平（保证所有副本无分歧）。`updated_at` 仅用于展示，**不参与**裁决（防时钟回拨，见 03 §5 混沌场景 4）。

---

## 3. Lamport 时钟规则

- 每设备维护计数器 `lamport`；本地每次写操作 `+1` 并记入 oplog 与实体行。
- 拉取到远端 op 时：`local = max(local, remote) + 1`。
- 新设备通过恢复短语/账号初始化时从服务端取全量 op 历史重放，lamport 起点对齐。
- 墓碑 GC（§5.4）后新设备改由"快照 + 增量"初始化（§4.3）。

## 4. 同步协议 v1

### 4.1 oplog 记录

一条字段级变更 = 一条 op：

```jsonc
{
  "device_id": "dvc_9f2…",
  "lamport": 1042,
  "entity": "task",
  "entity_id": "01912ab3-…",      // UUIDv7
  "field": "due_date",
  "op": "set",                    // set|del
  "value": { "t": "date", "v": 20650 },   // 密文模式下该对象整体加密为 value_blob
  "base_seq": 1030                // 客户端最后同步到的 seq（服务端用于冲突检测优化，可省略）
}
```

### 4.2 接口

```text
POST /v1/sync/push
  req:  { "device_id": "…", "ops": [Op…] }            // ≤500 条/批，按 lamport 升序
  resp: { "server_seq": 10440, "results": [ {"i":0,"accepted":true} … ] }

GET  /v1/sync/pull?since={seq}&limit=2000
  resp: { "cursor": 10441, "ops": [EncOp…], "has_more": false }
  // EncOp：value 密文 + lamport/origin 明文元数据

POST /v1/devices            // 设备注册：device_id、名称、公钥指纹
POST /v1/sync/snapshot      // 新设备初始化：申请快照位点（服务端打包 GC 后的存活实体）
```

### 4.3 同步流程

```text
本地写 → domain 校验 → 写 tasks 行 + 追加 oplog（同一事务）→ 触发 push
push: 取未确认 ops → 上报 → 服务端分配 server_seq（全局单调）→ 客户端回填
pull: 常驻轮询/推送唤醒 → since=last_pull_seq → 逐条:
        对端 lamport ≤ 本地该字段裁决值 → 忽略
        否则 → 应用 + local lamport 推进
服务端职责: 只做 序号分配 + op 存储/转发 + 字段裁决表维护（lamport/origin 明文）
客户端职责: 解密 + 合并；服务端永不接触明文负载
```

- **实时性**：常驻连接（WebSocket `/v1/sync/stream`，Phase 1 用 15s 轮询起步，Phase 2 升 WS + APNs/FCM 唤醒）。
- **断网**：oplog 本地累积，恢复后按批推送；拉取按 cursor 续传。
- **新设备初始化**：`snapshot` 位点 + 快照后增量，避免重放全部历史。

### 4.4 服务端存储（Postgres）

```sql
CREATE TABLE sync_ops (
  seq BIGSERIAL PRIMARY KEY,
  device_id TEXT NOT NULL,
  lamport BIGINT NOT NULL,
  entity TEXT NOT NULL, entity_id TEXT NOT NULL,
  field TEXT NOT NULL, op TEXT NOT NULL,
  payload BYTEA,                 -- 密文负载
  meta JSONB NOT NULL,           -- 类型/长度明文元数据（最小化）
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE TABLE entity_lamport (     -- 字段裁决表：服务端可见的最高 (lamport,origin)
  entity TEXT NOT NULL, entity_id TEXT NOT NULL, field TEXT NOT NULL,
  lamport BIGINT NOT NULL, origin TEXT NOT NULL,
  PRIMARY KEY (entity, entity_id, field)
);
```

服务端在 push 时对 `entity_lamport` 做原子 upsert（lamport 高者胜），被拒的 op 返回 `accepted:false` 并附当前裁决值，客户端据此回退重放——这保证**任何时刻任何副本拉取同一区间，重放结果一致**。

> **PoC 状态（W5–6）**：本节协议已在 `apps/server` 实现——`SyncStore` 抽象 + `MemorySyncStore`（单测/收敛 PoC）+ `PgSyncStore`（与上表同构，宿主机端口 5433）；双客户端经真实 HTTP handler 的收敛测试见 `apps/server/test/sync_convergence_poc_test.dart`（并发写、等时钟破平、改/删墓碑、删除复活、分页续传、stale ack 六场景）。payload 当前为明文 JSON，E2EE 密文化于 S08 落地。

## 5. 冲突解决细则

| 场景 | 规则 |
| --- | --- |
| 同字段并发写 | 字段级 LWW（lamport 优先，origin 破平）——报告 §6.3 |
| 不同字段并发写 | 各自保留（字段级隔离的意义所在） |
| 并发改/删 | 删除胜，写入墓碑；改方下次拉取收到 del 后丢弃 |
| `sort_key` 拖拽 | 单字段 LWW 天然成立（ADR-014）；两端同时拖同一列表按裁决取一 |
| 关系完整性 | 客户端 pull 后做外键修复（project 被删 → task 回收件箱；墓碑与孤儿策略见 §5.1） |
| 计数类（actual_minutes 累加） | 不用 LWW：time_entries 明细为事实源，汇总值可随时重算 |

### 5.1 墓碑与 GC

- 墓碑保留 90 天，之后服务端合并为 `entity_gc` 位点记录；快照初始化（§4.3）使新设备不依赖完整历史。
- 客户端本地墓碑 30 天后物理删除（需确认 `last_pull_seq` 覆盖该时段）。

### 5.2 验收红线（报告 §6.3，测试矩阵见 02 文档 §7.2）

- 多端并发编辑**零数据丢失**（混沌套件全绿）。
- 断网 7 天重连自动收敛。
- 日常使用同步流量 < 10KB/日（op 压缩 + 批量 + 仅增量）。
- 10k 任务库冷同步（新设备初始化）≤ 60s（4G 网络）。

## 6. E2EE 加密设计

### 6.1 密钥层级

```text
用户主密码 ──Argon2id(m=64MB,t=3,p=1)──► KEK（不出设备）
恢复短语(12词 BIP39) ──PBKDF2──► 主密钥 MK（KEK 丢失时的唯一恢复路径）
MK ──HKDF("db")──► 数据密钥 DK：逐行 XChaCha20-Poly1305 加密
MK ──HKDF("backup")──► 备份密钥（服务端每日备份再加密层）
每设备随机生成 DeviceKeyPair（Ed25519）：设备身份与轮换签名
```

- 注册：服务端只存 `MK 的 Argon2 参数 + 验证器 + 加密包裹的 MK`（用 KEK 包裹后上传）。
- 换密码 = 解包裹 MK → 新 KEK 重新包裹上传；**历史密文不变**。
- 丢密码 = 仅恢复短语可救；产品上强制引导用户抄录短语（S12 私测前完成流程测试）。

### 6.2 加密范围与明文元数据

| 内容 | 处理 |
| --- | --- |
| op 负载 / 实体字段值 | XChaCha20-Poly1305 密文（AEAD，nonce 随机 24B） |
| lamport、origin、字段名、entity 类型 | 明文（裁决与路由必需）——字段名泄露面可接受，记录于隐私政策 |
| FTS 索引 | 仅本地；不上传 |
| 时间戳精度 | 元数据时间戳截断到小时，降低侧信道（对齐最小化原则） |

### 6.3 BYOK 与本地模式的关系

E2EE 与 BYOK（AI 侧）相互独立：E2EE 保护**同步通道与服务器存储**；BYOK 控制**AI 请求用什么模型、谁付费**。本地模式（AI 总开关关闭）下两者均不触网。

## 8. 兜底方案：PowerSync 切换标准

自研同步保留成熟第三方兜底（报告 §6.3）。切换触发条件（满足任一即评估，4 周内出结论）：

1. S08 末混沌套件仍非全绿；
2. 私测期出现 1 例确认的数据丢失且根因在同步引擎；
3. 同步引擎缺陷修复累计消耗 > 1 人月/季度（维护成本越界）。

切换影响评估：PowerSync 不原生提供 E2EE——届时降级为"TLS + 服务端全盘加密 + 零知识承诺"并在隐私政策中如实披露，属产品级权衡，须 P0 批准。
