# 程簿（Agendum）革命性改进蓝图

- 日期：2026-10-09
- 前置：[深度调研与系统性批评](2026-10-09-深度调研与系统性批评.md)（下称「批评报告」）
- 定位：这不是 bug 清单的延伸，而是对仓库发展方式的**一次反转**。批评报告 §6 列出的内核资产全部保留、不重写；革命针对的是「信任模型、健壮性策略、诚实机制」三个层面。

## 0. 革命主张：从「文档驱动的愿景仓库」反转为「信任驱动的产品」

现状的本质（批评报告 §0/§2.4）：仓库按「什么容易生成」在生长——文档、评估集、演示页先涨；按「文档声称什么」在自评——E2EE、AI 原生、服务端零明文都写进了 ADR 和 README，但没有一件在运行时为真。继续在这个轨道上加 sprint（S08、S09…），每一步都在放大声称与现实的裂缝。

三条反转原则，优先级高于任何功能路线图：

1. **不可信服务端原则（Zero-Trust Server）**：服务端的威胁模型默认是「会被攻破/会被运营商看」。加密是默认路径，明文是需要显式声明的开发模式。凡是由客户端自报就能绕过的控制（byok、level、device_id），都不是控制。
2. **同步免疫原则**：同步内核的收敛性已经证明，缺的是免疫系统——最坏输入（毒丸、重复、乱序、升级代差）的代价必须是「损失一条 op + 可观测的死信」，而不是「卡死一个设备」或「静默丢数据」。
3. **诚实工程原则**：凡写进 README/ADR 的声称，要么变成 CI gate，要么标注「未实现」。文档与代码的偏差必须可被机器发现，而不是等下一次深度审计。

## 2. R1 信任革命（S08，1-2 周）——把 E2EE 从库变成默认路径

这是全仓杠杆率最高的一步：密码学实现、codec 插座、设备注册端点全部已就绪（批评报告 §6.3），缺的只是接线与密钥管理闭环。

1. **客户端接线**：`store.dart` 建 SyncEngine 时传入 `E2eeOpCodec`；首次启动生成 BIP39 恢复短语 → Vault 派生 → oplog value 全部密文上服务器。
2. **密钥持久化**：引入 `flutter_secure_storage`（macOS Keychain / Linux libsecret），MK 不落 SQLite；本地库透明加密作为 R3 可选项（SQLCipher 或应用层字段加密）。
3. **设备鉴权**：push/pull 要求 Ed25519 签名挑战（密钥体系已在 `packages/e2ee/device.dart`）：服务端下发 nonce，客户端用设备私钥签名，服务端对照注册公钥验证。deviceId 伪造、额度冒用两类漏洞随之消失。
4. **租户隔离**：oplog 增加 owner（device 或 account 维度），pull 一律 `WHERE owner = authenticated_device`。改造点集中在 `pg_store.dart:128`、`memory_store.dart:49` 与 handler 中间件。
5. **多设备信封端点**：`POST /v1/vault/envelope`（上传 KEK 信封，密文服务端不可解）+ `GET`——第二台设备凭恢复短语解锁后即可同步，无需人工搬密钥。
6. **明文开发模式显式化**：`IdentityOpCodec` 只允许在 `AGENDUM_PLAINTEXT=1` 环境变量下启用，服务端对明文 payload 打醒目日志头。
7. **ADR-005 增补**：元数据明文面（时序 UUID、字段名、密文长度）作为已知取舍写入；entity_id 如需隐藏，规划 v2 换随机 UUID（注意与现有 oplog 的兼容成本）。

验收红线：**服务端数据库 dump 里不存在任何任务明文；无签名请求被 401；第二台设备 10 分钟内完成恢复短语接入。**

## 3. R2 同步免疫（S08-S09，与 R1 并行）

1. **逐 op 幂等键**：oplog 增加唯一约束 `(device_id, lamport, entity_id, field)`；服务端 upsert 去重；引擎读 `results[i].accepted`，被拒 op 本地标记不重推。消灭「ack 丢失 → 重复 op 膨胀」。
2. **snapshot 重同步通道**：落地 docs/03 §4.3 承诺的 `/v1/sync/snapshot`：新设备/游标落后过多/死信过多时全量对账，替代「cursor 已越过就永远丢了」的现状（批评报告 §1.3 B3）。
3. **未知实体的版本协商**：握手时交换 schema 版本；未知实体 op 不再「跳过 + 推游标」，而是记入待补队列，升级后由 snapshot 补齐。
4. **服务端入口校验**：op 字段白名单 + value 类型校验（server 是第二道防线，客户端已强转）。毒丸即使进来，也止步于一条死信。
5. **PG 裁决路径进 CI**：workflow 加 postgres service 容器，`pg_store_test` + 双端收敛测试在 CI 真跑（批评报告 §2.2）。
6. **db migration 测试**：用 drift_dev schema 导出 + `v1→latest` upgrade 用例锁死迁移行为；此后每次 schemaVersion+1 必须带迁移测试（进 code review checklist）。
7. **墓碑与 oplog GC**：docs/03 §5.1 的 90 天合并/30 天物理删落地，配合 snapshot 通道做「GC 后新设备兜底」——否则 oplog 无限增长会先于商业化杀死 Postgres。
8. **时区语义决策**（ADR）：due_date 明确「浮动日期」（无时区，随设备本地日历解释）还是「固定时区」；GTD 语义下推荐浮动日期 + 明确文档化，`domain/dates.dart` 收敛为纯函数注入时区。

## 4. R3 诚实化机制（持续，成本极低）

1. **「声称-实现」对账表**：批评报告 §2.1 的漂移矩阵转为 `docs/reviews/adr-drift.md` 活文档；每条 ADR 标注 `已落地/部分/未落地`；新 ADR 合并时必须填状态列。
2. **文档决策二选一**：每个未落地 ADR 要么删（承认换方案，写新 ADR），要么排进 roadmap。现状（文档描述一个不存在的仓库）是所有选项里最差的。建议：ADR-002 顺势落地 Riverpod 3（反正 store.dart 已到重写临界点，见 R4-3）；ADR-003 删除 Dart Frog 声称，承认 shelf（够用且已验证）。
3. **README 数字自动化**：测试数、评估集数、包列表由脚本从仓库实况生成（`make docs-stats`），README 只引用，不再手写。108→222 的漂移不再可能。
4. **评估集去自证**（批评报告 §1.6）：①口径改诚实——README 只写总 92%，删除「rule_solvable 100%」的说法；②引入 30-50 例**非作者标注**用例（访谈真实语料、或让另一个无实现上下文的 AI 会话独立标注）；③`title_contains` 逐步收紧到 `title_exact`，zh-042「到 开评审会」这类坏例转为已知缺口清单；④落地 capture 遥测（docs/04 §9 的 `capture_used`）让 bad case 回流。
5. **CI 收口**：action SHA pin + `permissions: contents: read`；`make ci` 与 PR-CI 的包列表从同一来源（Makefile MEMBERS）生成，消灭「本地全绿 ≠ CI 全绿」。
6. **Linux 闭环**：`flutter create --platforms=linux`（MIGRATION §2.7 的悬而未决项，建议：入库）；golden 测试去 macOS 路径，用 `GoogleFonts` 打包字体或 asset 字体重建 Linux 基线；迁移验收 `make ci` 真跑一次并记录到 MIGRATION。

## 5. R4 产品核（S09+）——「AI 原生」先要是一个好 GTD

1. **状态机补 doing**：`domain/status.dart` 增加 doing 及流转表（next→doing→done/waiting/back），今日视图「现在，做这件事」点击即 doing，焦点卡与状态机终于咬合。带 migration v4。
2. **焦点算法 v0**：`today_focus(tasks, now)` 纯函数——overdue > 今日 due > 无日期 next（按手动排序），替换 `tasks.first`；配套 10 个单测。今日列表 where 排除 done，已完成项单独折叠区（与 README 走查声称对齐）。
3. **客户端状态层换 Riverpod 3**（兑现 ADR-002）：替换 TaskStore 的 7 份全量缓存与 `_reload` 风暴（批评报告 §4），drift watch 流直供视图。这是最重的一块，建议独立分支一次做完，期间冻结 client 功能。
4. **捕获条可修正**：解析 chips 可点击（日期/项目/标签 chip 点击弹出候选与清除）；落库前确认步可跳过但错 解析可一行修正。目标：错解析的修正成本从「重打全文」降到「点一下」。
5. **NLP 缺口清单转 issue**：「月底/周末/下午三点/X点一刻」、2月30日静默滚动、周六视角「这周三」——按批评报告 §3.4 逐条建卡，规则引擎先保证「不解析错」，解析不了就留原文（现有 `ambiguities` 机制很好，继续用）。
6. **计划重定基线**：docs/01 的 6 人 39 sprint 计划改为「单人 + AI 会话」版本——范围裁剪到「捕获 + 同步 + E2EE + 今日焦点 + 拆解师（唯一 AI 引擎）」，其余引擎移入「愿景」文档并明确标注未排期。**宁可小而真，不可大而假。**

## 6. R5 AI 真实化（R4 之后）

1. **一个真适配器**：先接 OpenAI 兼容协议（BYOK 直连，服务端不过手 key——顺便消灭 BYOK 凭证管理问题），`/v1/ai/parse` 的 L3 走真模型，回传与规则引擎同构的结构化结果。
2. **BYOK 服务端化**：`byok` 不再是请求体布尔，改为服务端校验的凭证（签名请求天然携带）；额度账本落 Postgres（复用 sync 的存储层），device 鉴权后按 owner 记账。
3. **拆解师 MVP**：六引擎只做一个——任务拆解，输出结构为子任务数组，走黄金评估集同款 harness 评质量。其余五引擎的文档移入愿景区。

## 7. 执行顺序与依赖

```
R0（已落地大部分） ──→ R1 信任革命 ──┐
                └──→ R2 同步免疫 ──┼──→ R4 产品核 ──→ R5 AI 真实化
R3 诚实化（持续，随每个批次携带） ←──┘
```

- R1 与 R2 可并行（触碰文件面基本不相交：R1 在 e2ee/client/server 鉴权层，R2 在 sync/db/server 存储层）。
- R4-3（Riverpod）必须在 R1/R2 稳定后单独做，避免三线同改 client。
- 每批次退出标准写进对应 milestone；R1/R2 各自的验收红线见上文。

## 8. 明确不做的事

- **不重写同步内核**：LWW + Lamport + 全序重放的收敛性已证明且有测试，是全仓最强资产（批评报告 §6.2）。换 CRDT 是用新风险换旧风险。
- **不先做五端**：macOS/iOS 之外的端在信任与产品核完成前没有意义。
- **不追求 100% 规则解析率**：规则引擎的边界靠「不解析错 + 可修正 + bad case 回流」管理，不靠堆正则到 500 例。
- **不删文档**：愿景文档降级标注，不销毁——它们包含真实的产品思考，错的是把它们当成了现状。
